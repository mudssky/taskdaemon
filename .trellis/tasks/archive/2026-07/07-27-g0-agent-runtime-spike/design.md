# G0 Agent 运行时技术 spike — 研究设计

> 本任务是研究型任务，本文替代常规 `design.md`，定义**验证方法**而非实现设计。

## 1. 为什么需要这个 spike

路线图 §5 把 runtime 接入写成了结论，但五项关键事实**从未实测**：

1. Pi 与 OMP 各自提供哪些能力 → 决定 gateway 的规模（可能相差数倍工作量）
2. **两者差异有多大** → 决定 `AgentRuntime` 抽象是否可行、抽到哪一层
3. SDK 是否真实可用、冷启动延迟多少 → 决定 G3 的设计方向与 G2 的池化策略
4. gateway 是否需要自己的持久化 → 决定 G2 是「服务」还是「代理」
5. 部署形态 → 决定 G2 能否开工

**这些问题不实测就写 design，G1/G2/G3/G4 会全部返工。**

## 2. 研究原则

| 原则 | 说明 |
|---|---|
| **实测优先** | 不接受「文档上说」。每条结论标注验证方式与观察到的现象 |
| **允许否定结论** | 「这个能力不需要做」「这个抽象不可行」「这个假设是错的」是**正当产出** |
| **两个 runtime 平等对待** | 不预设 Pi 是主、OMP 是次。差异是检验抽象的资产 |
| **零代码污染** | 验证脚本只放 `research/`，不进 `services/` 与 `apps/` |
| **实测优于文档** | 不符时以实测为准，并记录差异供未来升级参考 |

## 3. 验证方法设计

### 3.1 能力盘点（R1，对 Pi 和 OMP 各做一遍）

对每项能力设计一个**最小可观察实验**：

| 能力 | 实验设计 | 观察指标 |
|---|---|---|
| 会话持久化 | 起会话 → 发几轮 → 杀进程 → 重启 → 尝试恢复 | 历史是否还在？会话 ID 可复用？状态存在哪个文件/目录 |
| 多会话并发 | 同时起 N 个会话 | 一进程多会话还是 N 进程？内存占用曲线 |
| 工具调用可见性 | 触发一次工具调用，抓完整事件流 | 事件里有无 tool 名、入参、结果原文 |
| thinking 事件 | 用会触发推理的 prompt | 事件流中有无中间态 |
| abort 语义 | 长任务中途 abort | **是真停了还是只断了监听**（看 CPU / token 消耗） |
| 模型切换 | 会话中途切模型 | 是否需重建会话？历史是否保留 |
| **非 coding 可用性** | 不给 workspace/cwd 起会话，做纯对话任务 | 能否正常工作？是否强制要求文件系统 |
| 错误形态 | 故意用错模型名 / 让工具失败 | 错误以什么事件形式出现 |

**关键动作**：每次实验的**原始事件流**存成 JSONL 到 `research/samples/<runtime>/<capability>.jsonl`。这些样本后续直接用作 G3 的测试 fixture —— 一份工作两处用。

### 3.2 能力差异与抽象可行性（R3，本任务的核心判断）

这是新增的、也是最重要的分析。方法：

**第一步：并排对照表**

| 能力 | Pi | OMP | 差异性质 |
|---|---|---|---|
| … | | | 一致 / 语义不同 / 一方缺失 |

**第二步：对每项差异问三个问题**

1. 能否用 `RuntimeCapabilities` 的一个布尔或枚举字段声明掉？→ 能则无需抽象层介入
2. 能否用「接口方法设为可选 + capabilities 声明」处理？→ 次优解
3. 两者语义差异大到无法用同一接口表达？→ **危险信号**

**第三步：危险信号的处置选项**

| 选项 | 何时用 |
|---|---|
| 缩小接口 | 取两者交集，牺牲的能力通过 adapter 特有扩展点提供 |
| 拆分方法 | 一个概念拆成两个语义明确的方法，各自可选 |
| 不纳入抽象 | 该能力不进 `AgentRuntime`，由上层按 adapter id 特殊处理（**最后手段，会破坏中立性**） |

**第四步：给 G1 的明确结论**

- 两份填满的 `RuntimeCapabilities`
- 路线图 §5.2 的接口草案：**够用 / 需增加什么 / 需删除什么**

### 3.3 接入方式与延迟（R4）

两条路径都实测，不预设答案。

**冷启动延迟测量方法**：

- 测量点：`createSession` 发起 → runtime 可接受第一个 prompt
- **重复至少 10 次取分布**（min / median / p95），单次数据在冷启动场景毫无意义
- 分别测「进程已预热」与「完全冷启动」两种情况
- 记录环境（机器配置、是否首次加载模型配置等）

**首字节延迟**：prompt 发出 → 第一个事件到达。这个指标直接影响用户感知。

**协议异常实测**（CLI 路径）：半包、粘包、超长行、非法 JSON、进程中途退出，各造一次，记录观察到的现象。

**结论必须支撑**：`coldStartCost` 判定 + 池化策略建议（是否预热、预热几个、空闲保留多久）。

### 3.4 gateway 规模判定（R5）

对路线图 §5.8 的**七项职责**用判定表逼出结论：

| 职责 | Pi 覆盖 | OMP 覆盖 | gateway 需做 | 工作量 | 依据实验 |
|---|---|---|---|---|---|
| 会话↔进程编排 | | | | S/M/L | |
| 非交互调用入口 | | | | | |
| thread/run 持久化 | | | | | |
| 对外协议转换 | | | | | |
| **多 adapter 抽象与能力协商** | — | — | | | |
| 策略执行 | | | | | |
| usage/audit 产出 | | | | | |

**每格必填，「不确定」不是合法值。**

**两 runtime 覆盖度不同时的处置**：取交集？按 adapter 差异化？还是 gateway 补齐弱的一方？这个决策直接影响 G2 的复杂度，必须明确。

### 3.5 Pi WebUI 拆解（R9）

**前提**：路线图 §5.9 已决策参考重写并简化，本项不重开选型。

拆解方法：

1. 核实仓库地址与**许可证**（参考重写也要确认许可证允许）
2. 跑起来，**按用户旅程记录交互形态**（不是读代码结构）
3. 每个功能点问四个问题：
   - 解决什么问题？
   - 我们的场景有这个问题吗？
   - 依赖 Pi 的哪个私有接口？
   - **它假设了什么？**（一定有 workspace？一定支持 steering？一定单 runtime？）
4. 输出分级：`G4 必要` / `G5 增强` / `不需要`

**三份清单都有价值**：

- 功能分级表 → G4 的实现范围
- Pi 耦合点清单 → G1 需在标准协议下补齐的内容
- **单 runtime 假设清单** → G4 必须做成能力驱动而非硬编码的地方

## 6. 边界

**做**：实测、记录、判定、回写路线图假设。

**不做**：任何 `services/` 或 `apps/` 的实现代码；契约的正式冻结（归 G1）；企业鉴权方案调研（路线图 §6 已裁定移出仓库）；第三个 runtime 的调研（路线图 §12）。

## 7. 风险

| 风险 | 处置 |
|---|---|
| Pi SDK 不存在或不可用 | 有价值的结论 → 转 CLI 路径，记录并修订路线图 §5.6 |
| **OMP 无非交互模式，无法被程序驱动** | **重大风险** → 若成立，需回到路线图重估「初版两个 adapter」的决策，或换一个第二 adapter |
| 两者差异大到抽象不可行 | 按 §3.2 第三步的三个选项处置；最坏情况回路线图重估抽象层设计 |
| 实验做成了「读文档」 | 每条结论必须有「观察到什么」，评审逐条检查 |
| 范围失控做成实现 | 硬约束：`git status` 除 `research/` 与路线图外无变更 |
| 延迟测量只做一次 | 明确要求 ≥10 次取分布（§3.3） |
| 结论推翻路线图假设后不同步 | DoD 要求修订路线图并在 §16 追加记录 |
| Pi WebUI 拆解变成代码阅读 | 明确要求**按用户旅程**记录交互形态（§3.5） |
